## 1. What was blocked, and what changed

PR #17 recorded CR2 as `IMPLEMENTATION_BLOCKED_REFERENCE_UNAVAILABLE`: the study-written Python CR2 and Satterthwaite code **ran**, but there was no independently maintained implementation in the tested environment to check it against, so its output could not support a production choice or a method-comparison claim.

That dependency is now installed and pinned. **R 4.6.1** with **clubSandwich 0.7.0** — written by other authors, maintained independently of this project, and not written for this study — now serves as the reference.

**This closes an engineering gap, not a scientific one.** What follows is an implementation-agreement result. It says the Python code computes what clubSandwich computes. It says nothing about whether CR2 is the right estimator for HYP-01.

## 2. How the two implementations were made to see the same numbers

The fixtures are **not** regenerated in R. There is one generator — `make_fixture` in `tools/hyp01_inference_feasibility.py`, already committed and validated — and R consumes its output:

1. `export_fixtures.py` serialises all 18 fixtures to a strict-JSON interchange file carrying only the outcome vector, design matrix, coefficient names, cluster labels, target coefficient, fixture id and expected refusal status.
2. Missing values are encoded as JSON `null`, never as a sentinel number, so a missing outcome cannot silently become a zero on either side.
3. Each fixture carries a SHA-256 over a **language-neutral canonical string** (`%.17g` per double, `NA` for missing, fixed field order). R rebuilds that string from the values it parsed and recomputes the digest independently. **All 18 verified.** A reordered, truncated or altered fixture fails there.
4. Numeric results travel back as `%.17g` **strings**, not JSON numbers. jsonlite writes doubles at about 15 significant digits, which would have made the reported discrepancies partly a measurement of the JSON writer; `%.17g` round-trips an IEEE-754 double exactly, so what is reported below is the difference between the two computations.

## 3. Specification — resolved explicitly, not left to defaults

| Question | Resolution |
|---|---|
| Intercept | The design matrix carries its own column of ones. The fit is `lm(.y ~ 0 + ., ...)` so R does **not** add a second intercept |
| Coefficient ordering | As exported; column *j* ↔ `coefficient_names[j]`, no reordering |
| Cluster ordering | `factor(labels, levels = unique(labels))` — first-appearance order, not locale-dependent alphabetical sorting |
| Target coefficient | The slope on the synthetic regressor (index 1) |
| Null value / confidence level | 0 / 0.95 |
| Missing values | `na.action = na.fail`. R's default `na.omit` would have **silently dropped** the row and returned a number — a false agreement |
| Leverage adjustment | CR2 = the Bell–McCaffrey / Pustejovsky–Tipton bias-reduced linearisation. clubSandwich computes `A_g` internally; this bridge neither supplies nor overrides it |
| Working model | `target = NULL`, the identity working model for an unweighted `lm` — the same homoskedastic-independent model the Python side assumes |
| Matrix tolerance | clubSandwich's internal inversion tolerance is **not** overridden. Python clips eigenvalues of `(I − H_gg)` at 1e-12. These are different mechanisms and were left different on purpose |

One argument's resolved default is not visible from `formals()`: `inverse_var`. Rather than assert what it resolves to, the bridge computes the CR2 covariance **both ways** on every fixture. Maximum difference across all of them: **2.08 × 10⁻¹⁶**. The branch does not matter here, which is what the identity working model predicts.

## 4. Result — 13 of 13 admissible fixtures agree

Every fixture the Python implementation admits was compared under the tolerances **preregistered in PR #17 and used exactly as written**. None was loosened, reinterpreted or replaced.

| Field | Worst absolute difference | Worst relative difference | Preregistered tolerance |
|---|---|---|---|
| CR2 covariance matrix | 1.735 × 10⁻¹⁶ | 7.220 × 10⁻¹⁴ | rtol 1e-10, atol 1e-12 |
| Target variance | 3.990 × 10⁻¹⁷ | 3.962 × 10⁻¹⁵ | rtol 1e-10, atol 1e-12 |
| Standard error | 1.943 × 10⁻¹⁶ | 1.936 × 10⁻¹⁵ | rtol 1e-10, atol 1e-12 |
| t-statistic | 2.887 × 10⁻¹⁵ | 2.944 × 10⁻¹⁵ | rtol 1e-9, atol 1e-11 |
| p-value | 8.882 × 10⁻¹⁶ | 5.989 × 10⁻¹⁵ | rtol 1e-9, atol 1e-12 |
| Satterthwaite df | 7.105 × 10⁻¹⁵ | 1.262 × 10⁻¹⁵ | *see §5 — not preregistered* |

Agreement is at the floating-point noise floor, four to six orders of magnitude inside the tolerances.

## 5. One honest gap in the preregistration

The PR #17 tolerance set defines degrees of freedom as `exact_integer_equality`. **That rule was written for CR1**, whose inference df is the integer *G* − 1. The Satterthwaite df is continuous, so the preregistered rule cannot express agreement on it, and **no preregistered tolerance covers this field**.

Rather than quietly borrow a tolerance intended for another quantity, a separate one — rtol 1e-8, atol 1e-10 — is declared in `compare_reference.py`, labelled `preregistered_in_pr17: false`, and reported separately. It was fixed in source before the comparison was executed for the first time. Readers should treat the Satterthwaite df row above as evidence gathered under a **new** rule, not under the PR #17 preregistration.

## 6. Refusal fixtures — the reference was never forced to produce a number

| Fixture | Python | clubSandwich / `lm` | Classification |
|---|---|---|---|
| `F05_near_collinear_full_rank` | `ILL_CONDITIONED_DESIGN` | aliased coefficient `b2_aux` | `REFUSED_BY_BOTH` |
| `F06_exactly_rank_deficient` | `RANK_DEFICIENT_DESIGN` | aliased coefficient `b2_aux` | `REFUSED_BY_BOTH` |
| `F07_zero_variance_predictor` | `ZERO_VARIANCE_PREDICTOR` | aliased coefficient `b1_x` | `REFUSED_BY_BOTH` |
| `F09_missing_value` | `NONFINITE_VALUE_PRESENT` | `na.fail`: missing values in object | `REFUSED_BY_BOTH` |
| `F08_perfect_fit` | `DEGENERATE_FIT_RESIDUAL_VARIANCE_AT_NOISE_FLOOR` | **computes**, warning "essentially perfect fit" | `REFERENCE_BEHAVIOR_DIFFERENCE` |

Four fixtures are refused by both. **The stated reasons are not identical, and that is not a defect**: the two implementations reach the same refusal through different diagnostics. Python screens the condition number, the column variance and the residual variance explicitly; R discovers the same degeneracies as aliased coefficients during the QR fit.

**F08 is a genuine behaviour difference and is reported as one.** R returns an estimate of 1.9999999999999998 with a standard error of 3.97 × 10⁻¹⁷ — a number that is arithmetically produced but not usable — after warning that the fit is essentially perfect. Python refuses by a prespecified relative-residual-variance threshold. **Neither side was adjusted to make this agree.** The reference was not forced to refuse, and Python's refusal rule was not relaxed. On this fixture the Python output is simply not validated, because there is nothing meaningful to validate it against.

## 7. What is still NOT validated

**CR3 and the restricted wild cluster bootstrap-t remain `UNVALIDATED_STUDY_IMPLEMENTATION`.** They run; they have no independent reference here. clubSandwich does implement CR3, but this PR validated only the CR2 + Satterthwaite path that was actually compared, and `fwildclusterboot` was deliberately **not** installed.

**CR2 agreement is never treated as evidence about CR3 or the bootstrap.** Those are different estimators with different adjustment matrices; agreement on one says nothing about the others.

## 8. What this evidence does and does not support

Supported, exactly:

> **The study-written Python implementation agrees with the independent clubSandwich reference on the prespecified synthetic fixture matrix under the preregistered tolerances.**

Not supported, and not claimed anywhere in this PR:

- that CR2 is scientifically optimal, or better than CR1, CR3 or the bootstrap;
- that CR2 is approved, selected, or production-eligible;
- that HYP-01 will be significant, or that the study is adequately powered;
- that F5 is closed;
- anything at all about real data — none was read.

The size behaviour reported in the PR #17 grid is unchanged by this work and remains what it was: CR1 over-rejects in all four null cells tested, and the CR2 columns of that grid were produced by the same Python code validated here. **Validation makes those columns trustworthy as arithmetic. It does not make them a method-comparison result**, because the grid was never designed as a prespecified comparison and no uncertainty analysis of between-method differences was performed.

## 9. Reproducing this

```
python tools/hyp01_r_reference/run_validation.py --out <artifact.json>
```

One command: export fixtures, run the R reference, recompute the Python side, compare, write the artifact, exit nonzero on any unexplained mismatch. R and its packages are installed beforehand per [`r-packages.lock.json`](../tools/hyp01_r_reference/r-packages.lock.json); the validation itself makes no network request.

`test_market_response_hyp01_r_reference_validation.py` executes this bridge and recomputes the comparison rather than reading the artifact's declarations. Where R is unavailable it verifies everything that does not require it and says plainly which assertions were skipped — it never reports a pass it did not earn.
